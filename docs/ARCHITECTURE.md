# Backline: how the code is laid out

A map for finding things fast. Every source file starts with a `//!` summary; this page ties them together.

## The shape of it

- **One app struct.** `App` (in `backline/src/main.rs`, declared through `app_state!`) holds all state: each field written once, with what it starts as (`= value`; none: its type's default), and `App::new` builds it through `App::start`. Settings live in
  `settings.rs`: `load_settings` reads `settings.json`, `restore_settings` puts them back at start, `save_settings`
  writes them. A new setting = a field in `app_state!` (with `= value` unless it starts empty), then one line in `plain_settings!` (settings.rs) when it's kept under its own name as it is (or clamped), else one line in each of `restore_settings` and `save_settings`.
- **Actions.** UI code never changes state directly for anything non-trivial: it pushes an `Action` (enum in
  `main.rs`); `actions.rs` carries it out after the frame (`apply`: playing, the queue, the library, the windows;
  `apply_extra`: practice, tunes, the diary, tools).
- **Messages.** Background threads send a `Msg` (enum in `main.rs`) on `app.tx`; the main loop takes them in once a
  frame (`messages.rs`: `drain`, then `drain_extra`).
- **The frame.** `update` (main.rs) draws the overlays and picks the view: the mini player, Now Playing, the
  full-window visuals, or the library with the player's column (`ui/layout.rs`, `main_layout`). Test copies:
  `test_hooks.rs` (BACKLINE_OPEN pages, BACKLINE_SHOT pictures).
- **Pages are `impl App` blocks in their own files.** `ui/views.rs` keeps the navigation (section bar, ALL PAGES)
  and the music pages (files, YouTube, SoundCloud, lists, My Tracks, the queue's header); its parts are child
  modules beside it: `ui/tunes.rs`, `ui/diary.rs`, `ui/loops_page.rs`, `ui/practice.rs` (the practice panel),
  `ui/text_field.rs` (the text box), `ui/notes_box.rs`. Song lists and Tidal pages: `ui/tracks.rs`; covers:
  `ui/images.rs`; search matching: `data/search.rs`; window chrome (app bar, drag handles): `ui/chrome.rs`; the
  app's icon and fonts: `ui/app_look.rs`.
- **Saved data.** Settings (window, skin, toggles) in `settings.json`; everything you build up (tunes, loops,
  playlists, diary days, hearts, YouTube/SoundCloud lists) in `library.json` via `data/store.rs` (`Store`). Both under
  `%APPDATA%\Backline` (`api::config_dir()`; `BACKLINE_HOME` overrides it for test profiles). SYNC keeps its own
  sync.json there (never synced: `data/sync.rs`).
  Stored songs are `cache/<track id>.<ext>`; their title, artist, album and cover are written into the file's own tags
  in the background (`cache::know` / `start_tagging`, from the liked list, playlists and songs played), and offline
  the songs are listed from those tags (`cache::tagged`).

## Adding things

- **A tab under LINES / CHORDS:** add it to a group in that file's `GROUPS` (a new number) and a branch for its number.
- **A text box:** reserve an `F_*` id in `ui/tools.rs`, call `views::field(ui, &mut self.ed, F_ID, &mut text, rect, hint, multi)`.
- **A saved per-song thing:** a field on the relevant `store` struct with `#[serde(default)]` so old files still load.

CROSSFADE (2026-11-26): Settings' Crossfade (`xfade`, 0 = off, 2-12 s). In `update`, once the song is within that many seconds of its end and the next one is downloaded ahead (`prefetched`), it moves on with `fade_next` set; `play_index` then sends `Cmd::PlayFade` instead of stopping. The player keeps the old sink in `fading` (cosine down) while the new one comes in (sine up); `Ctl::song` numbers the songs so only the one coming in moves the position, loops and clicks (`Looper`). Never with repeat-one or an A-B loop; pause, stop or a new device end a crossfade at once.

GAPLESS (2026-11-26): with crossfade off, in a song's last 8 seconds the next one (downloaded ahead) is handed to the player (`Cmd::Queue`, the app's `armed`), which appends its whole chain to the same sink behind the song playing, its `Looper` made with `Looper::queued`: it takes over the song number, position and rate only as its first sample is asked for (`Ctl::began`). The player then sets `Shared::advanced`; the app moves on with `gapless_next` set, so `play_index` catches up without stopping or sending the song again. A change of plan (the next song isn't that one any more, a loop or repeat-one, crossfade turned on) sends `Cmd::Unqueue`: the lined-up song ends before it begins and the normal ending takes over. Play, Stop and a new device call it off too.
